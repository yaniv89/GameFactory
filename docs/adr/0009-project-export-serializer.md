# 9. A real ProjectDocument → PlayerProjectData serializer, not docs/SPEC.md Section 7's on-disk format

Date: 2026-08-16

## Status

Accepted

## Context

Two shapes exist in this repo for "a Forge project," and nothing converts between them:

- **`ProjectDocument`** (`packages/editor/src/store/projectStore.ts`) — what the editor actually authors and persists: `scenes` (id, name, flat row-major `tiles`, `entities`), `installedModules` (`Record<name, FormValues>`), `activePack`/`packOverrides`/`packTerrainRemap`. This is real, undoable, server-persisted state (`POST /api/v1/projects/{id}/revisions`).
- **`PlayerProjectData`** (`packages/player/src/playerProjectData.ts`) — what `forge export` embeds and the standalone player boots from: `scenes` (near-identical shape), `installedModules` as an array with `version` + resolved `config` + embedded `guestBundleSource`, plus `projectId`/`buildId`/`schemaVersion`/`engineVersion`/`startSceneId`.

`packages/cli/src/commands/export.ts`'s `runExport` only resolves each declared module's `guestBundleSource` from `node_modules` (`hydrateProjectData`) — its input, `ExportProjectInput`, is *already* `PlayerProjectData` shape minus that one field. `ExportOptions.projectPath`'s own doc comment says it plainly: *"Not the editor's own ProjectDocument shape (there is no serializer from that to a file yet ... fixtures/projects/\* are hand-authored ExportProjectInput files directly, same as this command expects)."* `moduleManifests.ts`'s own comment says the same thing from the editor side: *"There's no build pipeline yet to carry this config into a published game (M6) ... installing and configuring a module here is real, undoable project state that has no runtime consumer yet."*

Practical consequence: M6's file:// export proof (`packages/player/test-browser/`, `fixtures/projects/starter-rpg`) exercises a hand-authored fixture, never a game actually built in the editor. **A creator cannot play or export what they build.** This is the highest-value gap in the platform — everything downstream (publish-to-a-URL, the marketplace, Play services) is moot if the editor's own output never reaches a player.

### What this ADR is *not*

`docs/SPEC.md` Section 7 describes a much larger on-disk format: a multi-file directory tree (`project.json`, `scenes/*.scene.json`, `entities/*.entity.json`, `graphs/*.graph.json`, RLE-encoded tilemap layers, a full entity-component system with module-namespaced components, triggers, `forge.lock`). None of that exists in the actual editor — no ECS on the document side, no triggers, no graphs, no RLE encoding, no lockfile. Building Section 7 for real would be a multi-milestone project of its own, disconnected from what the editor actually authors today.

This ADR scopes down to the concrete, load-bearing gap: converting between the two shapes that are *actually implemented and actually used*. Section 7 remains aspirational future work, explicitly out of scope here — this serializer is not a down payment on it and should not be mistaken for one.

### Design questions this ADR has to answer

Four real gaps surfaced while tracing the two shapes, none of which have an existing answer to defer to:

1. **Per-module config.** `inventory`/`turn-battle` have real `configSchema`s (`moduleManifests.ts`) whose `FormValues` already mirror `SetupContext.config` 1:1 (that file's own comment: *"mirrors what each module's SetupContext.config actually reads ... not a fictional example"*) — a direct passthrough. `dialogue` has no `configSchema` at all (trees aren't flat-form-editable); its real config must be *synthesized* from `EntityPlacement.dialogue` across every scene, into `{ trees: [{ id: entity.id, nodes: [{ speaker, text }] }] }` — the exact shape and the exact `treeId == placementId` convention `PreviewApp.tsx`'s `rebuildDialogueRuntime` already uses for the unsandboxed preview, and the exact convention `gameLogic.ts` already emits (`dialogue:start` with `treeId: nearestId`) expecting the real dialogue module's guest code to resolve it. Two module "kinds" (form-passthrough vs. entity-synthesized), not one.
2. **`version` per installed module.** `ProjectDocument.installedModules` is `Record<name, FormValues>` — no version is stored anywhere. `ExportProjectInput` requires a non-empty `version` string per module.
3. **`schemaVersion`.** `ProjectDocument` has no such field. `PlayerProjectData.schemaVersion` is required. `PERSIST_VERSION` (currently 5) is a distinct concept — zustand's local `persist` *storage*-migration marker, not a wire/document-format version, and must not be conflated with one (bumping it for a client-storage reason must not silently change what a published game claims as its schema).
4. **`buildId`.** Currently hand-picked per fixture (`"starter-rpg-golden"`). Needs a real generation rule.

## Decision

1. **New package, `@forge/project-export`**, owning both the *document* types (`ProjectDocument`, `SceneSummary`, `EntityPlacement`, `EntityDialogue`, `emptyTiles`, `migrateDocument` — moved here verbatim from `packages/editor/src/store/projectStore.ts`) and the pure, isomorphic (no `node:fs`, no browser API) conversion function `toExportProjectInput(document, options): ExportProjectInput`. `ExportProjectInput`'s canonical definition also moves here from `packages/cli`, which imports it instead of redeclaring it. This is the opposite dependency direction from "the editor owns the document shape, everything else depends on the editor" — deliberately: neither the CLI nor a future server build worker should have to depend on the whole editor SPA (React, Vite, Dockview, ...) just to know what a project document looks like, the same reasoning `@forge/module-api`'s own "zero dependencies, nothing depends the wrong way" discipline already applies elsewhere in this repo. `projectStore.ts` re-exports the moved types/helpers from `@forge/project-export` (`export type { ProjectDocument, ... } from "@forge/project-export"`) so none of the 11 files elsewhere in the editor that import them from `projectStore.ts` today need to change — only `projectStore.ts` itself does. `@forge/project-export` depends on `@forge/player` (for `PlayerProjectData`/`PlayerInstalledModule` types); `packages/editor` and `packages/cli` both depend on `@forge/project-export`.
2. **Per-module export adapters, keyed by module name**, inside `@forge/project-export`: a `Record<string, (document: ProjectDocument, config: FormValues) => Record<string, unknown>>`. Default (no entry) is passthrough — `FormValues` used as-is, correct for `inventory`/`turn-battle` today and for any future module whose `configSchema` already mirrors `SetupContext.config`. `@forge/dialogue` gets the one real adapter: aggregate `trees` from every scene's NPC `EntityPlacement.dialogue`, across the whole project (a module is installed once; its config is shared across all scenes, matching multi-scene support already shipped for `scene:changed`). **`PreviewApp.tsx`'s `rebuildDialogueRuntime` tree-building logic moves into this shared adapter** (currently duplicated logic, single-scene only) rather than staying triplicated across preview/export/a future server build worker — the preview calls the same adapter now.
3. **`version` resolves from the installed package's own `package.json`** at conversion time (Node-side wrapper in the CLI, not the pure function itself, which takes a `resolveModuleVersion(name): string` callback) — the same place `guestBundleSource` already resolves from (`require.resolve` against `packages/player`'s `node_modules`), and the same "local/workspace-resolved version of a future registry-backed resolution" pattern `ExportProjectInput`'s own doc comment already names as the intended migration path.
4. **`schemaVersion` becomes a real constant** exported by `@forge/project-export` (`CURRENT_PROJECT_SCHEMA_VERSION = 1`), stamped by the serializer — independent of `PERSIST_VERSION`, which stays a `packages/editor`-local concern. Future `ProjectDocument` shape changes that need to survive into an export bump this constant and get a migration function in this package, the same discipline `migrateDocument` already applies for local persistence, kept as a separate concern on purpose (a client-storage migration and a wire-format migration are not always the same event).
5. **`buildId` is a fresh random id generated per export**, not content-derived — this is the local/CLI export path; a server build worker's own build-identity strategy (content-addressed vs. random) is C1's decision, not this one, and this ADR does not pre-empt it.
6. **`engineVersion` resolves from `@forge/core`'s own `package.json` version** at conversion time, via the same resolution mechanism as `version` above, replacing the hand-picked `"0.0.0-m6"` fixture placeholder.
7. **`ExportProjectInput` remains a valid, still-accepted `forge export` input** (existing fixtures, hostile-input tests, and CI's file:// proof keep working unmodified) — `forge export` gains a second, additive input path that accepts a real `ProjectDocument` and runs it through `toExportProjectInput` first. Wiring that second path into the CLI and the editor, and re-proving the M6 exit criterion against a genuinely editor-built project, is the next task (not this one) — this ADR and its implementation are scoped to the pure serializer and its own unit tests against hand-constructed `ProjectDocument` fixtures, proven correct in isolation before anything downstream depends on it.

## Consequences

- The editor's own state can, for the first time, actually become a playable/exportable game — closing the platform's highest-value gap.
- `PreviewApp.tsx` and the new serializer share one tested implementation of dialogue-tree synthesis instead of two independent, silently-driftable ones.
- Two module "kinds" (passthrough vs. adapter) is a real asymmetry a third-party module author will eventually hit — today it's invisible because only three first-party modules exist and only one needs synthesis. When the registry-backed publish pipeline (C-track) lets third parties declare non-flat config, this adapter registry either grows a real per-module extension point in `@forge/module-api` (its own ADR, per CLAUDE.md 3.1 — a Module API change) or a documented convention for what "flat FormValues passthrough" actually promises. Not decided here; flagged so it isn't silently assumed away.
- `schemaVersion`/`buildId`/`engineVersion`/module `version` all move from "hand-authored fixture literal" to "really computed" — the `starter-rpg` fixture's current hand-picked values stop being representative once the CLI's new path exists, which is exactly what the next task re-proves against real Chromium.
- No change to `@forge/module-api`'s public surface, the sandbox, auth, or the CSP — this ADR does not require the CLAUDE.md 6.1 stop-and-wait gate, and none was taken.
