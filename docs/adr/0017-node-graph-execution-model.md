# ADR 0017: Node-graph execution model and sandbox implications

## Status

Accepted (M1 of the J1 authoring-layer milestone, CLAUDE.md Section 8). Resolves `docs/SPEC.md` Section 22 Open Question 1 ("should the graph VM be Turing-complete?"), which has been open since the spec was first written.

## Context

`@forge/module-api`'s own `ForgeModule` interface already declares `defineGraphNode(def: GraphNodeDefinition): void` on `SetupContext` (`docs/SPEC.md` Section 9.3) and the example module manifest (Section 9.2) already lists a `provides.graphNodes` array — the graph system was designed into the API surface from the start, deliberately left unimplemented (`packages/module-api/src/module.ts`'s own doc comment: "no graph VM exists yet — Section 22 Open Question 1 is still open"). J1 is where that gets built.

The stakes are the same ones every other milestone in this project answers first before writing code, restated for this one specifically:

- **What does a graph actually compile to, and where does it run?** A node graph expressive enough to build "a new mechanic" (M6's own exit criterion) is, functionally, a second way to author runtime behavior — the same thing a hand-written `ForgeModule` already does. CLAUDE.md guardrail 1 ("never execute third-party module code in a trusted context") and guardrail 2 (no `eval`/`new Function` outside the sandbox) don't stop applying just because the graph's *author* is the project's own creator working inside Forge's own first-party editor, rather than a marketplace module author. A creator's graph is not first-party engine code; it needs the identical isolation a hand-written module already gets, for the identical reason.
- **How expressive can a graph be before it stops being safe or debuggable?** SPEC's own Open Question 1 already leans toward "bounded loops with an iteration cap, no recursion" — this ADR needs to actually decide that, not just note the lean.
- **How does a third-party module add its own node types (M4) without becoming a second, uncoordinated API surface** alongside `@forge/module-api`'s own additive-only, semver-versioned discipline (CLAUDE.md Section 3.1 — "the single most important structural discipline in the repo")?

Existing, load-bearing precedent this decision builds on rather than invents from nothing:

- **`docs/security/SANDBOX-DESIGN.md`**: the QuickJS-in-a-Worker boundary, the JSON-only `__hostCall`/`__hostCallAsync` capability bridge, the separate function-handle mechanism (`__forge_addSystem`, `__forge_addInterceptor`, `__forge_eventsOn`) that lets the host call back into guest-registered callbacks without ever letting a live reference escape the VM that produced it, and the per-tick compute/memory/stack budget (`setInterruptHandler`/`setMemoryLimit`/`setMaxStackSize`) already measured and proven to actually stop a hostile infinite loop or allocation bomb, not just documented as a plan.
- **`@forge/dialogue`** (`packages/modules/dialogue/src/index.ts`) is already, structurally, a graph interpreter: it receives dialogue trees as plain JSON data via `ctx.config.trees` (validated and skip-on-malformed, never trusted blindly), and interprets that data at runtime using nothing but the ordinary public `ForgeModule` surface — `addSystem`, `events`, `runInterceptor`, `defineComponent`. It proves, today, in production code, that "a creator-authored graph of nodes, given as data to a sandboxed first-party module" is not a hypothetical shape — it already works for one specific kind of graph (a branching dialogue tree). This ADR generalizes that exact pattern rather than inventing a new one.
- **CLAUDE.md Section 2.2**: "Node graph | React Flow 11 | Do not build a graph library" — the *editor UI* is settled tooling; this ADR is entirely about what happens after a creator finishes wiring boxes together in that UI, not about the UI itself (M3's job).
- **`docs/adr/0015`** (entity/component model) names the node-graph authoring layer directly as the reason it moved away from a closed `kind: player-start | npc` union: "adding a vehicle, a mount, an enemy, or a weapon pickup as a placeable entity means widening this union and re-touching all nine sites, every time, forever — the closed-union version of the exact 'chained to certain choices' problem raised when planning the node-graph authoring layer." The same anti-pattern applies here: a node-type registry closed to only what ships with the engine would recreate that exact problem at the logic layer instead of the entity layer, which is precisely what M4's third-party extension point exists to avoid.

## Decision

### 1. A graph is data, compiled to a registration, never to host-executed code

A node graph — the editor's own React Flow document (nodes, typed sockets, edges, per-node config values) — is JSON. It is never compiled to a JavaScript (or any other) source string that gets `eval`'d or `new Function`'d anywhere, on the host or in the guest. "Compile" (M5) means: validate the graph's shape (referenced node types exist in the registry, socket types match across every edge, no illegal cycle — see Decision 3), then hand the resulting JSON document, verbatim, into a new first-party runtime module: **`@forge/graph-runtime`**.

`@forge/graph-runtime` is built against `@forge/module-api` only, the same rule CLAUDE.md Section 9.1 design rule #1 already holds every first-party module to ("everything a first-party Module can do, a third-party Module can do") and the same rule `tools/security/check-module-boundaries.mjs` already enforces in CI for `@forge/dialogue`/`@forge/inventory`/`@forge/turn-battle`. It receives one compiled graph document per graph instance as its own `ctx.config` (exactly how `@forge/dialogue` already receives `config.trees`) and interprets it using nothing but `addSystem`, `addInterceptor`, `events`, and `world` — the same public surface, running inside the same QuickJS sandbox, subject to the same per-tick compute/memory/stack budget, that every hand-written module already runs under.

This means a graph — however it was authored, by however trusted or untrusted a creator — can never do anything a hand-written module couldn't already do, because it never gets a wider surface than `ForgeModule` grants. There is no new sandbox, no new bridge, no new class of trust boundary. A hostile or simply broken graph is bounded by exactly the mechanisms `docs/security/SANDBOX-DESIGN.md` Section 2.1 already measured working against a hostile hand-written module: an interrupted tick, a caught out-of-memory, a module suspended and attributed by name — never a hung tab or a host-process compromise.

**What this rules out, explicitly:** compiling a graph to a JS/TS source string for the host to `eval` (a direct CLAUDE.md guardrail 2 violation, full stop, regardless of how sanitized the string looks) and compiling a graph to native ECS systems registered directly against the *host's* `@forge/core` scheduler, bypassing the sandbox entirely because "the graph is just data, not really code" (the same reasoning error CLAUDE.md's own worked example already rejects — a manipulated prompt from N7's own security review is not "just text" either, once something downstream treats it as an instruction).

### 2. `@forge/graph-runtime` is one first-party module, not one module per graph

A project can have many graphs (one per quest, one per mechanic). `@forge/graph-runtime` is installed once per project (the same way `@forge/dialogue` is installed once and handles every dialogue tree in `config.trees`, not once per tree) and receives the full list of compiled graph documents in its own config. Each graph gets its own namespaced systems/interceptors/event subscriptions at `setup()`, keyed by the graph's own id — one Worker, one `QuickJSRuntime`, N interpreted graphs, matching `docs/security/SANDBOX-DESIGN.md` Section 3's "each Worker hosts exactly one module's runtime" rule (a graph is not a module in its own right for isolation purposes; it's data inside one).

### 3. Expressiveness: bounded loops only, no recursion — resolving Open Question 1

`docs/SPEC.md` Section 22 Open Question 1's own lean is adopted as the actual decision: **the graph node library ships no general-purpose loop node and no node that lets a graph invoke another graph (or itself).** The only iteration constructs are structurally bounded by construction, not by a runtime check that could be gotten wrong:

- **"Repeat N times"**, where N is a literal configured at authoring time and validated against a fixed ceiling (a real number, tuned during M2 implementation against the same per-module frame-cost budgets `docs/SPEC.md` Section 18 already sets, not guessed here) — never a graph-computed, runtime-variable N.
- **"For each entity matching \[query\]"**, bounded by the query's own result size — already a naturally bounded quantity (a world's entity count is itself bounded), the same shape `SystemDefinition.query`/`EntityView` already give hand-written systems.

This is a real, additional restriction on top of the per-tick compute budget that already exists (Decision 1) — not a replacement for it, a second independent control on the same risk, the pattern this codebase already leans on repeatedly (`docs/adr/0012`'s "two controls on one threat, not redundant" reasoning, `docs/adr/0016`'s rate-limit-plus-daily-budget). The compute budget is the backstop that catches anything this structural restriction misses; the structural restriction exists because the backstop's own failure mode — a system silently suspended mid-tick, every tick, forever — is a terrible experience for exactly the audience this feature is for. A non-programmer whose graph "just doesn't work, with no visible error" has no way to debug that; a non-programmer who literally cannot wire up an unbounded loop in the first place (M3's editor UI won't offer the node, and M5's validation step rejects a hand-crafted `.json` project file that tries anyway) has a shorter path to a working mechanic. Recursion (a graph calling itself, directly or through another graph) is dropped entirely, not offered and then bounded — a recursive graph-of-graphs call stack has no natural ceiling the way an entity-bounded `forEach` does, and nothing in M6's own exit criterion ("a non-programmer builds a new mechanic") needs it.

**What this means the v1 graph can express**: linear and branching data flow, conditionals, bounded iteration over an explicit count or an entity query, reads/writes through `world`, triggering and responding to events, and reading/writing component data — a real, useful subset, not a toy. **What it explicitly cannot express**: general recursion, unbounded loops, or a graph that calls another graph as a subroutine. This is the same "deliberately trimmed, not silently incomplete" discipline `docs/adr/0012` Decision 1 already models (v1 covers images only, not audio/fonts, and says so) — a real scope decision, stated as one, not discovered later as a gap.

### 4. Node type registration reuses `defineGraphNode` exactly as already specified — no new plugin mechanism

`SetupContext.defineGraphNode(def: GraphNodeDefinition): void` (already declared in `docs/SPEC.md` Section 9.3, not a new addition this ADR is proposing) is how a node type becomes available for `@forge/graph-runtime` to interpret. Registration happens the same way `defineComponent`/`addSystem`/`addInterceptor` already do: inside a module's own sandboxed `setup()`, called by whichever module — first-party or, once M4 ships, third-party — owns that node type. `@forge/graph-runtime` itself builds the runtime node registry the same way the engine already builds the component/system/interceptor registries during world construction: by collecting what every installed module's `setup()` registered, before any graph starts interpreting.

This gives M4 (the third-party extension point) for free, structurally, rather than as separate work: a marketplace module that calls `defineGraphNode` inside its own `setup()`, declares the resulting node type name(s) in its manifest's existing `provides.graphNodes` array (already shown in the Section 9.2 example manifest, unchanged), is indistinguishable at the runtime-registration level from a first-party node type. No second plugin-loading mechanism, no new manifest field, no new capability. `GraphNodeDefinition` itself lives in `@forge/module-api`, gets the same additive-only/semver discipline as every other type there (CLAUDE.md Section 3.1), and — mirroring `defineComponent`'s own editor-schema-plus-runtime-shape split — carries two halves: a runtime half (`execute(ctx, inputs): outputs`, the pure function `@forge/graph-runtime` actually calls) and an editor half (socket types, label, category, icon) that ships in the module's separate `entry.editor` bundle (Section 9.2's own existing split), never the runtime bundle — a published game must never ship node-authoring UI metadata any more than it ships the rest of a module's editor code today.

### 5. The editor validates; the runtime never trusts that it did

M3's React Flow UI is where a creator is stopped from building something invalid in the first place — type-mismatched sockets refuse to connect, a cyclic data-flow graph (as opposed to the bounded-loop constructs Decision 3 explicitly allows) is rejected at wire-time, an unbounded-N "repeat" is clamped in the UI itself. But the compiled JSON document a project actually ships is just a file, and `docs/SPEC.md`'s own unifying input-handling rule (CLAUDE.md Section 4.6 / `docs/security/THREAT-MODEL.md` Section 3.4) is that nothing the server or the runtime receives is trusted because a well-behaved client produced it. M5's compile step re-validates the graph document from scratch — referenced node types actually exist in the registry that got built, sockets actually type-check, every loop bound actually resolves to a literal under the configured ceiling — against a hand-edited or malformed project file exactly as rigorously as against one the editor itself produced. A validation failure here is `@forge/graph-runtime`'s own equivalent of `@forge/dialogue`'s `validateTrees`: skip the malformed graph, log why, keep the rest of the world running — never a hard crash over one bad graph, the same "one bad input isn't a verdict on the whole batch" reasoning `Forge.Functions.ArtGen`'s own variation-batching (N3) already uses.

### 6. Performance attribution: a graph is accounted the same way a module already is

`docs/SPEC.md` Section 9.4's profiler requirement ("errors are attributed to the specific module, version, and author responsible" — CLAUDE.md Section 5.3) already demands per-module frame-cost attribution. A graph interpreted inside `@forge/graph-runtime` gets attributed by graph id *within* that module's own budget, the same way `@forge/dialogue` already logs which malformed tree it skipped by id — a creator whose own graph is expensive sees "graph 'boss-fight-logic' cost 1.8ms this tick," not an opaque "`@forge/graph-runtime` is slow." This needs real implementation work at M5 (the attribution hook doesn't exist yet), but no new mechanism — it's the identical per-module cost tracking `docs/SPEC.md` Section 18's own per-module budget table already requires, scoped one level finer.

## Consequences

- **What this unlocks:** a real path to M6's exit criterion — a non-programmer builds a genuinely new mechanic using only the graph, with the same security posture every hand-written module already has, no new trust boundary for `docs/security/THREAT-MODEL.md` to carry (the graph's *data* is a new input source in the technical sense, but its *execution* introduces nothing THREAT-MODEL.md doesn't already cover for module code in general — this gets a short amendment noting the new input source, not a new threat-table row the way `docs/adr/0016`'s art-generation work needed one).
- **What stays out of scope, honestly:** general recursion and unbounded loops (Decision 3 — a real, permanent limitation of the v1 graph, not a "later" item); quests and data tables (named in J1's own title alongside the node graph) are a separate authoring surface built *on top of* this execution model once it exists, not designed here; a graph debugger/step-through UI (useful, not required for M6's own exit criterion, which only needs a graph to *work*, not to be debuggable step-by-step).
- **New dependency:** none. React Flow is already pinned (CLAUDE.md Section 2.2); `@forge/graph-runtime` is a new first-party package built against already-pinned tooling, not a new external dependency.
- **Task split going forward:** M2 (the core ECS primitive node library — the bounded set of node types every graph can use without any module installed: entity create/destroy, component get/set, event emit/listen, comparisons, math, the bounded-iteration nodes from Decision 3), M3 (the React Flow editor UI, wired to M2's library, doing the authoring-time validation Decision 5 describes), M4 (formalizing `GraphNodeDefinition` in `@forge/module-api` and proving a third-party-shaped node type end-to-end, per Decision 4 — mostly already implied by M2/M3's own shape, made explicit and tested here), M5 (the actual compile/validate step plus `@forge/graph-runtime` itself, per Decisions 1-3 and 5-6), M6 (real exit criterion: a real or simulated non-programmer builds a new mechanic, graph-only, the same "5 real people" rigor M4's own original 10-minute-build exit criterion used).

## Addendum (M4): `defineGraphNode` formalized, with a real (not stubbed) sandbox bridge

`GraphNodeDefinition`/`GraphNodeExecutionContext`/`GraphSocketDefinition`/`GraphSocketType` moved from their provisional home in `@forge/graph-nodes-core` (M2) to `packages/module-api/src/graph.ts` — the permanent, additive-only/semver-disciplined surface (CLAUDE.md Section 3.1), regenerated through `api-extractor`'s real `api-update`/`api-check` (`etc/module-api.api.md`), not hand-edited. `SetupContext.defineGraphNode(def): void` is a real member of the interface now, no longer the "deliberately absent — Section 22 Open Question 1 still open" line `module.ts`'s own doc comment used to carry.

Per Decision 4, node-type registration follows the identical pattern `defineComponent`/`addSystem`/`addInterceptor` already established — this was not a new bridge mechanism to invent, and it wasn't left as a type-only stub either:

- **`packages/runtime-host/src/module/graphNodeRegistry.ts`**: a new `GraphNodeRegistry`, shared across every `ModuleBridge` in one project exactly the way `World`/`Scheduler`/`EventBusImpl`/`InterceptorRegistry` already are (`ModuleBridgeOptions` gained a required `graphNodes` field, threaded through the four real call sites: `moduleBridge.test.ts`'s harness, `saveCoordinator.test.ts`'s harness, `smokeRunner.ts`, and `packages/player/src/gameLogic.ts`'s real boot path).
- **`ModuleBridge`'s `__forge_defineGraphNode`**: `type`/`inputs`/`outputs` cross as plain JSON (same shape `__forge_defineComponent`'s schema/defaults already use); `execute` crosses as a live, `.dup()`'d guest function handle stored in `ownedHandles` — the same "a function isn't JSON-serializable, so the host calls back into guest code later" treatment `__forge_addSystem`/`__forge_addInterceptor` already get (`docs/security/SANDBOX-DESIGN.md` Section 4.2), not a new trust shape.
- **A real duplicate-registration guard**: two modules registering the same node `type` fails the second module's `setup()` with an attributable error naming both modules, rather than silently letting one overwrite the other.
- **`packages/editor/src/preview/directModuleHost.ts`** (the editor's separate unsandboxed live-preview host, first-party-modules-only per its own doc comment) got the same `defineGraphNode` member — a plain in-memory `Map`, no JSON marshaling needed since there's no host/guest boundary there — so `SetupContext`'s widened shape doesn't silently break live preview.

**What M4 proves, stated honestly against what it doesn't:** `packages/runtime-host/test/moduleBridge.test.ts` gained four real-QuickJS tests (no mocking) proving a module — including one deliberately named and shaped like a marketplace package (`@acme/loot-tables`, built only against the public `SetupContext`, exactly as `@forge/dialogue` already is per this ADR's own Context section) — can call `ctx.defineGraphNode(...)` inside its sandboxed `setup()` and have the registration land correctly, attributed to the right module, with a genuinely live and intact `execute` function handle. What M4 does **not** do: invoke `execute()`. There is still no established wire protocol for marshaling a `GraphNodeExecutionContext` (`world`/`events`/`next`/`warn`) across the host/guest boundary to a running interpreter — inventing one now, with no real consumer to validate it against, would be exactly the kind of speculative bridge work `docs/adr/0012`'s "deliberately trimmed, not silently incomplete" discipline warns against. That protocol is `@forge/graph-runtime`'s (M5's) own job, not guessed at here.
