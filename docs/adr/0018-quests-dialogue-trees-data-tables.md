# ADR 0018: Quests, branching dialogue trees, and data tables

## Status

Proposed. Covers the three remaining, unstarted pieces of J1's own title (CLAUDE.md Section 8): "Authoring layer — node graph, quests, branching dialogue, data tables." The node-graph piece is done (`docs/adr/0017`, M1–M6). Per CLAUDE.md's own "Adding to the Module API" session template — this ADR is written before any code, specifically because one of the three (data tables) needs a real, additive `SetupContext` change. Nothing in `packages/module-api` is touched until this is agreed.

## Context

`docs/SPEC.md`'s own content-model table (Section 15, the one CLAUDE.md 2.2's "Node graph | React Flow 11" and "Tables | TanStack Table v8 | Data table editor" tech-stack rows already provision for) states plainly:

| Content type | Covers | Compiles to |
|---|---|---|
| Node Graph | Quests, cutscenes, dialogue trees, event logic | Compiles to the restricted bytecode VM, not to JS |
| Data Tables | Items, skills, enemies, loot | Spreadsheet UI, CSV import/export, formula column support |

Two things follow directly from that table, and this ADR takes both at face value rather than re-deciding them from nothing:

1. **Quests are not a fourth authoring surface — they're graphs.** SPEC groups quests with cutscenes/dialogue-trees/event-logic under the same "Node Graph" row, not a separate one. `@forge/graph-runtime` (M5/M6) already exists, is proven end to end through the real sandbox, and is exactly "the restricted bytecode VM" SPEC's own table means (it isn't literally bytecode — `docs/adr/0017` Decision 1 already settled that a graph is data interpreted by a first-party module, never compiled to executable code on the host or in the guest — but it's the one JSON-graph execution engine this row's four content types share). Reinventing a second graph engine for quests specifically would contradict the row SPEC itself draws around them.
2. **Data tables are a genuinely separate, general-purpose surface** — a spreadsheet, not a graph — with its own row in the same table, its own pinned tech (`CLAUDE.md` 2.2's TanStack Table), and a stated requirement (CSV import/export) nothing built so far touches.

**Branching dialogue** sits slightly outside that table's own framing and needs its own look: `@forge/dialogue` (M3) already *runs* a fully branching tree — `DialogueTreeConfig.nodes[].choices[].next` (`packages/modules/dialogue/src/types.ts`) is a real branch-and-jump structure, and `dialogueModule`'s own event handling (`dialogue:choose`, multi-node advance, auto-advance) already interprets it correctly; none of that is new work. What's missing is authoring: `EntityPlacement.dialogue` (`packages/project-export/src/documentTypes.ts`) is `{speaker: string; text: string}` — one line, no `choices`, no second node — and `buildDialogueTreesFromEntities` (`moduleAdapters.ts`) always synthesizes a one-node tree from it. The gap is a UI gap, not a runtime one, and this ADR treats it that way: no module-api change, no new runtime module, no new export-adapter shape beyond widening one field's type.

### Why branching dialogue doesn't become graph-authored too

Given quests reuse the graph engine, the obvious question is whether dialogue trees should too (SPEC's own table lists them in the same row). Rejected, for a reason specific to this project's own design law, not a general one: CLAUDE.md 5.1's "the editor is a workshop, not a toy" and 5.3's "direct manipulation beats forms" both point at matching a tool to what's actually being authored. A dialogue tree is a linear-with-branches *conversation* — a list of lines, each with 0–4 choices, each choice pointing at another line. Forcing that through React Flow's typed-socket node-wiring canvas (drag a `core:onEvent`-shaped box, wire a `speaker` string port by hand) would be authoring friction for content that's naturally a list, not a graph — the same mismatch CLAUDE.md 12.9 already warns against in the other direction ("make the editor look more like a game engine"). Quests, by contrast, genuinely are event-driven state machines with real branching *logic* ("has the player killed 3 wolves AND talked to the elder?") — the shape graphs already exist to express, and forcing a bespoke quest-DSL editor instead would duplicate `@forge/graph-runtime`'s own investment for no authoring-experience gain.

## Decision

### 1. Quests: a first-party `@forge/quests` module, driven by the existing graph engine

**Static definition vs. dynamic logic, split the same way a `GraphDocument` already splits data from behavior:**

- **`ProjectDocument.quests: Record<string, QuestDefinition>`** (new document field, alongside `graphs`) — a quest's *static* shape: `{id, name, description, objectives: {id, description}[]}`. Purely descriptive data an author fills in once, shown in a new `QuestsPanel` (mirroring `GraphsPanel`'s own list-with-create/delete pattern exactly).
- **`@forge/quests`** (new first-party module, built against `@forge/module-api` only, same boundary rule every other first-party module already follows) owns the *dynamic* state: a `QuestState` component (per-player, numeric/boolean fields only per `docs/SPEC.md` Section 4.2 — `active: boolean`, and one boolean per objective index, capped the same bounded way `core:repeat`'s own ceiling is, since a component's field count is fixed at `defineComponent` time, not runtime-variable) plus events (`quest:start`, `quest:completeObjective`, `quest:completed`) other systems and graphs can observe.
- **The actual logic — when does objective 2 complete, what happens on quest completion — is authored as an ordinary graph**, using three new additive `@forge/graph-nodes-core` node types: `core:questStart` (config: `questId`), `core:questCompleteObjective` (config: `questId`, `objectiveId`), `core:questIsActive`/`core:questIsObjectiveComplete` (pure, for branching on quest state). These are ordinary impure/pure node types, no different in kind from `core:emitEvent`/`core:getField` — they just happen to call into `@forge/quests`' own event surface instead of the generic `ctx.events` a hand-authored graph would otherwise need to know the exact event names for. `GraphsPanel`/`GraphEditorDialog` need zero changes to support this — the node palette already renders whatever's in `coreGraphNodes`.

**Why not a dedicated quest-graph "flavor"** (a second `@forge/graph-runtime`-like interpreter, specialized for quest state machines): rejected — it would duplicate M5's own compile/interpret work for a strictly narrower case, when three new node types plus one module reuses 100% of the already-built, already-sandbox-proven graph pipeline.

**Why quest state isn't just more `@forge/graph-runtime` state:** a graph interpreter is stateless by design (`docs/adr/0017`'s own "a graph is data, compiled to a registration" framing) — it reacts to events and reads/writes components, but owns no state of its own between activations. Quest progress must survive a save/reload (`docs/adr/0006`'s save-file discipline) the identical way `@forge/inventory`'s own storage does; a real module, not the interpreter, is what a save file's `globals[moduleName]`/component snapshot mechanism already knows how to persist.

### 2. Branching dialogue: a dedicated `DialogueTreeEditorDialog`, no module-api change

- **`EntityDialogue`** (`packages/project-export/src/documentTypes.ts`) widens from `{speaker, text}` to a real tree: `{id: string, nodes: DialogueTreeNode[]}` where `DialogueTreeNode` mirrors `@forge/dialogue`'s own `DialogueNodeConfig` shape field-for-field (`speaker, text, locale?, choices?: {id, text, next}[], autoAdvanceSec?`) — a **type-only** mirror the same way `packages/modules/graph-runtime/src/types.ts` already independently declares its own wire shape rather than importing across the module-boundary line (this package may only depend on `@forge/module-api`-adjacent boundary rules the same way — actually simpler here, since `project-export` has no such restriction, so this can be a direct type alias of `DialogueNodeConfig` re-exported, not a duplicate; still worth stating as a decision so a future editor doesn't wonder why they look identical).
- **`DialogueTreeEditorDialog`** (new component, `packages/editor/src/dialogue/`): a full-screen `Dialog` (matching `GraphEditorDialog`'s own shape) with a node list (add/remove/reorder lines), a per-node form (speaker/text/locale/auto-advance — the existing `JsonSchemaForm` machinery, same as every other config form in the editor), and a per-choice "which line does this jump to" picker (a `<select>` over the tree's own node list — deliberately simpler than the graph editor's keyboard connect-picker, since a dialogue choice has exactly one destination, not an arbitrary typed-socket wire).
- **`buildDialogueTreesFromEntities`** (`moduleAdapters.ts`) stops synthesizing a one-node tree and instead passes the authored tree straight through (a type-shape pass, not new logic).
- `@forge/dialogue` itself: **zero changes.** It already interprets exactly this shape.

### 3. Data tables: a new, additive `SetupContext.dataTables` capability

This is the one real module-api surface change, so it gets the full "problem, options, decision, consequences, additive?" treatment CLAUDE.md's own template asks for.

**The problem:** an item/skill/enemy/loot table (SPEC's own examples) is project data a *module or graph* needs to read at runtime — "look up row `sword_iron`'s `damage` column" — but nothing in `SetupContext` today hands a module anything beyond its own `config`. A data table isn't any one module's config (an item table is read by `@forge/inventory`, a loot table by whatever drops items, a stat table possibly by a hand-authored graph) — it's a shared project resource, the same category `ProjectDocument.graphs` and `ProjectDocument.installedModules` already are, just data instead of behavior.

**Options considered:**

- **(a) Bake each table into whichever module's config needs it**, per-consumer, at export time (e.g. fold an item table into `@forge/inventory`'s own `config.items`). Rejected: couples the data-table feature's usefulness to a hand-maintained mapping of "which module gets which table," breaks the moment a *graph* (not a module) wants to read a row, and contradicts the "a data table is a shared resource" framing above — SPEC's own hot-reload requirement ("Data table row | Patch the table. No restart", Section 18-adjacent live-reload table) also implies a table's consumers aren't fixed at author time.
- **(b) A new, additive `SetupContext.dataTables: Readonly<Record<string, readonly Readonly<Record<string, unknown>>[]>>`** — table id → its rows, each row a plain JSON object (column name → value) — delivered to every module's `setup()` the identical way `config` already is (JSON-serialized across the sandbox boundary, no new bridge mechanism: this is the same "plain data in, `ctx.X` out" shape `config` itself already uses, not a live callback like `addSystem`/`defineGraphNode`). Two new, additive `@forge/graph-nodes-core` node types — `core:lookupRow` (config: `table`, `key column`, pure, inputs: `{key: any}`, outputs: `{row: any}` or `undefined` if not found) and `core:tableRowCount` (pure, config: `table`) — let a graph query a table without a module in between, the same "graph reads project data directly" pattern `core:getField`/`core:getComponent` already establish.
- **(c) Each data table is its own tiny pseudo-module** (its own `ctx.config` "instance"). Rejected: a table isn't behavior — it has no `setup()` to run, no events to emit, no reason to exist inside the module-registration lifecycle at all; forcing it through that shape would be structure for structure's sake.

**Decision: (b).** `SetupContext` gains one new readonly field, additive, no existing member touched — the same "additive, semver-safe" bar CLAUDE.md 3.1/9.1 already holds every module-api change to, and (per CLAUDE.md's own template question) **yes, this is additive within the current major version**: every existing `ForgeModule`/`GraphNodeDefinition` keeps compiling and running unchanged; `dataTables` simply exists for whichever new code reads it.

- **`ProjectDocument.dataTables: Record<string, DataTableDefinition>`** (new document field) — `DataTableDefinition = {id, name, columns: {id, name, type: "number"|"string"|"boolean"}[], rows: Record<string, unknown>[]}`. A `DataTablesPanel` (new, list-with-create/delete, mirroring `GraphsPanel`/`QuestsPanel`) plus a `DataTableEditorDialog` built on **TanStack Table v8** (already pinned, CLAUDE.md 2.2 — this is precisely the "data table editor" row names) for the actual spreadsheet grid: add/remove row, add/remove column (with type), edit a cell inline.
- **CSV import/export**: a small, hand-rolled RFC 4180 reader/writer (quote-escaping, embedded commas/newlines) rather than a new dependency — CLAUDE.md Section 2 pins no CSV library, and the parsing surface needed here (a rectangular grid of typed cells, no formulas — SPEC's own "formula column support" is explicitly named as a stretch feature this ADR does **not** commit to building yet, flagged honestly rather than silently dropped) is small enough that hand-rolling stays within CLAUDE.md's own "the answer is a small local utility, not a dependency" default. If real-world CSVs turn out to need more (BOM handling, non-UTF8, multi-line quoted fields beyond the basics) that's a follow-up, not a blocker to shipping the table editor itself.
- **Export-time wiring**: `moduleAdapters.ts`-adjacent, but not a per-module adapter — `toExportProjectInput`/the export pipeline hands `document.dataTables` straight through as a new, always-present field on the export payload (every installed module and the sandboxed graph-runtime both receive the same `dataTables` regardless of install status, the same "no module has to opt in" treatment `ctx.log`/`ctx.storage` already get as "always present" capabilities in `SetupContext`'s own doc comments).

**Threat model note (`docs/security/THREAT-MODEL.md` gets a short amendment, not a new row):** a data table is authored by the project's own creator (first-party trust boundary, same as scene tiles/entity placements/graphs already are) and crosses into the sandbox as plain JSON the same way `config` does — no new trust boundary, no new input-validation surface beyond what `compileGraph.ts`'s own "never trust the editor already validated it" discipline already models for graphs; `@forge/graph-runtime`'s `core:lookupRow` node re-validates a `table`/`key column` reference against the actual received `dataTables` at execute-time rather than assuming the editor's own `DataTableEditorDialog` already guaranteed it exists.

## Consequences

- **What this unlocks:** the remaining three-quarters of J1's own stated scope, using nothing but reuse — `@forge/graph-runtime`, `GraphsPanel`'s list-panel pattern, `JsonSchemaForm`, and CLAUDE.md's own already-pinned TanStack Table — no new architectural risk class introduced (no new trust boundary, no new sandbox mechanism, no new cross-origin surface).
- **What stays out of scope, honestly:** formula columns in data tables (SPEC names it, this ADR defers it); a quest "prerequisite" graph UI shortcut (chaining `core:questIsActive` checks by hand in the graph editor is the v1 answer — a dedicated quest-dependency visualization is a future nicety, not required for a real quest to work); localized dialogue text beyond the `locale?` field `DialogueNodeConfig` already carries (translation *workflow* — CLAUDE.md 5.7's RTL requirement is already handled at the render layer, `@forge/richtext`, independent of this ADR).
- **New dependency:** none. TanStack Table v8 is already pinned; the CSV reader/writer is hand-rolled, not a new package.
- **Task split** (mirroring `docs/adr/0017`'s own M1–M6 numbering, continuing the same milestone sequence under J1 rather than restarting at 1):
  - **M7** — `@forge/quests` module (state component, events) + three new core graph nodes (`questStart`/`questCompleteObjective`/`questIsActive`+`questIsObjectiveComplete`) + `ProjectDocument.quests` schema.
  - **M8** — `QuestsPanel` UI (create/rename/delete a quest, author its objectives) — reuses `GraphEditorDialog` unchanged for the logic side.
  - **M9** — `EntityDialogue` schema widened to a real tree; `buildDialogueTreesFromEntities` updated; migration for existing single-line-authored projects (an old `{speaker, text}` becomes a one-node tree with no choices — lossless).
  - **M10** — `DialogueTreeEditorDialog` UI.
  - **M11** — `SetupContext.dataTables` (module-api, additive) + `ProjectDocument.dataTables` schema + `core:lookupRow`/`core:tableRowCount` graph nodes + export-pipeline wiring + `api-extractor` re-run (`etc/module-api.api.md`).
  - **M12** — `DataTablesPanel` + TanStack-Table-based `DataTableEditorDialog` + CSV import/export.
  - **M13** — Exit criteria, proven the same way M6 proved the graph engine: a real quest (start → objective → complete, graph-authored), a real branching dialogue (at least one choice point, authored through the new tree editor), and a graph reading a real data table row — each verified live in the preview via a real Playwright spec, not asserted.

Do not begin M11 (or touch `packages/module-api` at all) until this ADR is explicitly agreed — CLAUDE.md's own session template for module-api changes.

## Addendum (M7): `@forge/quests`, for real — one component per quest, not one field per quest

This ADR's own Decision 1 text named the state shape at a level that still left one real design question open: how does a single `QuestState`-style component, whose field count must be fixed at `defineComponent` time (`docs/SPEC.md` Section 4.2), represent an author-defined, per-project *set* of quests, each with its own author-defined objective count? The answer landed on here, and implemented in `packages/modules/quests/src/`:

- **One component per quest, not one component for all quests.** `@forge/quests`' `setup()` reads `config.quests` (a project's full, author-defined quest list — known and fixed the moment the module boots, never runtime-variable) and calls `ctx.defineComponent` once per quest, named `Quest_<questId>`. Each of those components has the *identical* fixed schema — `active: boolean`, `completed: boolean`, and sixteen `obj0..obj15: boolean` fields — regardless of how many objectives that specific quest actually declares. `MAX_OBJECTIVES_PER_QUEST = 16` is a real structural cap, the same kind Decision 1's own text pointed at with "capped the same bounded way `core:repeat`'s own ceiling is": a quest declaring more objectives than that gets the extras truncated, with an attributable `ctx.log.warn`, not a silent drop or a crash.
- **Objective identity is index-based inside the component, id-based at every boundary a graph or another module can see.** `objectiveFieldName(index)` maps a quest's `objectives[i]` to `obj<i>` for storage; every event (`quest:completeObjective`, `quest:queried`) and every graph node's `config` still addresses an objective by its real author-given `objectiveId` string — the index mapping is `@forge/quests`' own private implementation detail, established once at `setup()` time from the same `objectives` array order the author sees in `QuestsPanel` (M8).
- **Quest logic stays entirely in graphs, per Decision 1** — `@forge/quests` itself never decides *when* an objective completes. Four new, additive `@forge/graph-nodes-core` node types (`packages/modules/graph-nodes-core/src/nodes/quests.ts`) are the only way a graph touches quest state: `core:questStart`/`core:questCompleteObjective` (impure — emit `quest:start`/`quest:completeObjective`, exactly the shape `core:emitEvent` already has, just pre-aimed at `@forge/quests`' own fixed event names) and `core:questIsActive`/`core:questIsObjectiveComplete` (pure).
- **The pure-node state-read problem, resolved as this ADR's own earlier design work anticipated:** `GraphNodeExecutionContext` has no `storage` access — only `world`/`events`/`next`/`warn` (`packages/module-api/src/graph.ts`) — so a pure node reading quest progress can't call into `@forge/quests`' storage directly. It uses the same synchronous request/response pattern `@forge/inventory`'s `inventory:query`/`inventory:queried` already established for a host-side reader (`EventBusImpl.emit` calls every handler synchronously and in order — `packages/core/src/events/eventBus.ts` — so there is no async gap to bridge): `queryQuest()` subscribes to `quest:queried`, emits `quest:query`, captures the matching response by `entity`+`questId`, unsubscribes, and returns, all inside one `execute()` call. Zero changes to `@forge/graph-runtime`'s interpreter were needed — this is invisible to it, an ordinary node body using the `ctx.events` surface every node already has. If no `@forge/quests` instance answers (the module isn't installed), both pure nodes degrade to "not active"/"not complete" plus a `ctx.warn`, the same graceful-degradation treatment `core:getComponent` already gives a nonexistent component, never a throw.
- **Default-installed, mirroring `@forge/graph-runtime`'s own precedent exactly, for the identical reason:** `QuestsPanel` (M8) can't require a manual "install this module first" detour, and `@forge/quests` is safe with zero authored quests — `setup()` simply defines zero `Quest_<id>` components. `ProjectDocument.quests: Record<string, QuestDefinition>` (the static half — `id`/`name`/`description`/`objectives`) is a new document field alongside `graphs`, migrated to `{}` for any document that predates it, left untouched (never silently rewritten) for a document that already has one. `moduleAdapters.ts` gained a `"@forge/quests"` export adapter (`{quests: Object.values(document.quests)}`), the identical "aggregate the project's authored content into the module's real config" treatment `buildGraphRuntimeConfig` already gets.
- **Package structure deliberately mirrors `@forge/dialogue`, not `@forge/inventory`:** a real `dist/guest-bundle.js` (esbuild, IIFE, `platform: "neutral"`) and a `packages/player/package.json` devDependency entry, so `forge export`'s `require.resolve("@forge/quests/dist/guest-bundle.js")` resolves — proven for real by the CLI's own existing export smoke tests (`starter-rpg`, `marketplace`), which now export projects with `@forge/quests` default-installed and build a `file://`-loadable game from each, unchanged and still green. `@forge/inventory` has no such build (a pre-existing, separately-noted gap this ADR does not fix) — `@forge/quests`, like the node-graph system it's built on top of, needs the real sandboxed path from day one, so it follows the complete template instead.

**What M7 explicitly does not do, so M8/M13 don't inherit a silent gap:** the editor's own unsandboxed live preview (`PreviewApp.tsx`) does not yet run `@forge/quests` — that file wires each first-party module by hand (the same gap M5's own addendum noted for `@forge/graph-runtime` before M6 closed it), and `QuestsPanel`'s authoring UI does not exist yet either. Both are real, load-bearing pieces of M13's own exit criterion ("a real quest... verified live in the preview") and are M8/M13's job, not guessed at or stubbed here.

**Proof, not assertion:** `packages/modules/quests/test/quests.test.ts` (13 tests, fake-`SetupContext`, mirroring `@forge/inventory`'s own test harness shape) covers start/reject-unknown/reject-already-active/reject-already-completed, objective completion (including idempotent re-completion and the all-objectives-complete → `quest:completed` transition), query (including an entity with no state at all), and the `MAX_OBJECTIVES_PER_QUEST` truncation path. `packages/modules/graph-nodes-core/test/quests.test.ts` (8 tests) covers all four new node types against a fake `GraphNodeExecutionContext`, including a real query-round-trip fake responder and a case proving the pure nodes correctly ignore an unrelated `quest:queried` response and match only their own `entity`/`questId`. `packages/project-export/test/documentTypes.test.ts` and `toExportProjectInput.test.ts` cover the new `quests` document field's migration and export-adapter behavior. The full existing workspace test suite (`pnpm --filter forge test`, cascading through every dependent package including the editor's 446 tests and the CLI's real `forge export` smoke tests) stayed green throughout — no regression to dialogue, inventory, graph-runtime, or any other installed-module path from adding a fourth default-installed module.

## Addendum (M8): `QuestsPanel` — authoring a quest's static shape

Mirrors `GraphsPanel`'s own flat CRUD-catalog pattern (`packages/editor/src/panels/QuestsPanel.tsx`), not a new UI shape: a list of quests, each with a name+description form (`JsonSchemaForm`, both fields committed together on blur — the same "one form, submitted on blur" treatment `GraphsPanel`'s own name field gets, just with a second field since `QuestDefinition` has one) and a nested list of objectives (each a single-field form for its `description`). `QuestsPanelContainer`/`GraphsPanelContainer` in `DockviewPanels.tsx` are siblings, wired to the identical command-log-backed CRUD pattern `createGraph`/`renameGraph`/`deleteGraph` already establish in `projectStore.ts` — eight new `ProjectCommand` variants (`quest/create`, `quest/delete`, `quest/restore`, `quest/edit`, `quest/add-objective`, `quest/remove-objective`, `quest/restore-objective`, `quest/edit-objective`), each self-inverse or paired with its own opposite, all undoable through the same log scenes/graphs/modules already use.

**A real design question this milestone had to answer, not guessed at: how does an author actually *reference* a quest or objective from a graph node's `questId`/`objectiveId` config field, given both ids are `crypto.randomUUID()`-generated (the same "auto id, editable name" pattern `createGraph` already uses for `graphId`)?** Editable, human-typed slugs were considered and rejected for v1 — allowing `id` edits post-creation would require rekeying `document.quests`'s `Record<string, QuestDefinition>` and, more importantly, there's no existing precedent in this codebase for an internal id doubling as author-facing reference text (`graphId` itself is never surfaced for copying). The answer that ships: each quest/objective row shows its own id as a small, `user-select: all` styled `<code>` element (`.fg-quests-list__id`) labeled by a `title` explaining what it's for — a copyable reference, not an editable field. This is an honestly-scoped v1 answer, not a claimed-finished one: a friendlier cross-reference affordance (an autocomplete picker inside a graph node's `questId` config field, resolving against `document.quests` the way `GraphEditorDialog`'s own connect-picker resolves sockets) is real future UX work, out of scope for M8's own bar (an author *can* wire quest logic today, copy-paste and all).

**What M8 explicitly does not do:** no button here opens `GraphEditorDialog` or otherwise cross-launches the logic-authoring surface — per Decision 1's own "reuses `GraphEditorDialog` unchanged," an author creates a graph through the separate, already-existing `GraphsPanel` and wires `core:questStart`/etc. by hand. Whether that hop is discoverable enough for a genuine non-programmer is exactly the open question M13's own exit-criteria proof (a real quest, driven end to end) will honestly answer or surface as a gap — not assumed solved here.

**Proof, not assertion:** `packages/editor/src/panels/QuestsPanel.test.tsx` (6 tests) covers all six required states plus the create/edit/delete/add-objective/edit-objective/remove-objective interactions against the presentational component directly (`GraphsPanel.test.tsx`'s own pattern). `packages/editor/src/panels/QuestsPanel.stories.tsx` gives all six states a Storybook story (verified building cleanly via a real `storybook build`, not just typechecked). `packages/editor/src/shell/DockviewPanels.test.tsx` gained a `QuestsPanelContainer` suite (3 tests) proving quest/objective CRUD lands in real, undoable `document.quests` state, not local-only UI state — the same proof `GraphsPanelContainer`'s own suite already established for graphs. `packages/editor/src/store/projectStore.test.ts` gained 13 tests covering every new action (including undo/redo replaying a full edit sequence, mirroring the existing graph-edit-sequence test). `App.test.tsx` updated its own panel-count assertion (seven → eight, "Quests" now among them). The full editor suite (467 tests) and the CLI's real `forge export` smoke tests stayed green throughout.

## Addendum (M9): `EntityDialogue` widened to a real tree — and a real Immer constraint the ADR's own text didn't anticipate

`packages/project-export/src/documentTypes.ts`'s `EntityDialogue` moved from `{speaker, text}` to `{nodes: DialogueTreeNode[]}`, where `DialogueTreeNode` is `{speaker, text, locale?, choices?: DialogueTreeChoice[], autoAdvanceSec?}` and `DialogueTreeChoice` is `{id, text, next}` — field-for-field the same shape `@forge/dialogue`'s own `DialogueNodeConfig`/`DialogueChoiceConfig` already declare and already fully interpret (`dialogueModule`'s `showNode`/`dialogue:choose` handling, unchanged by this milestone, per Decision 2's own framing). `buildDialogueTreesFromEntities` (`moduleAdapters.ts`) now passes `entity.dialogue.nodes` straight through instead of synthesizing a one-node tree — the transformation this ADR described is gone because there's nothing left to synthesize.

**Deliberately no `id` field on `EntityDialogue` itself**, despite this ADR's own Decision 2 text sketching `{id: string, nodes: ...}`: the exported `@forge/dialogue` tree's `id` has always been synthesized as the owning `EntityPlacement.id` at export time (the `treeId == placementId` convention `PreviewApp.tsx`/`gameLogic.ts` already depend on), so a second, independently-authored id on `EntityDialogue` could only ever agree with or silently diverge from that convention. Dropping it avoids the divergence case entirely rather than guessing at reconciliation logic nobody asked for.

**A real, discovered-while-implementing snag with this ADR's other stated plan** — "a direct type alias of `DialogueNodeConfig` re-exported, not a duplicate" — didn't survive contact with the store: `ProjectCommand` values carrying an `EntityDialogue` flow through Immer's `set((state) => ...)` drafts (`projectStore.ts`), and Immer's `Draft<T>` cannot map a `readonly` array field nested inside a discriminated-union-typed command into its own mutable draft array type. `DialogueNodeConfig.choices` is `readonly DialogueChoiceConfig[]` (correctly so, for `@forge/dialogue`'s own sandboxed-config purpose) — aliasing it directly broke `dispatch`'s own type-checking the moment an `entity/configure`/`entity/add`/`entity/set-player-start`/`document/replace` command carried one. `DialogueTreeNode`/`DialogueTreeChoice` are independently declared instead (mutable `choices` array, otherwise identical), the same "type-only mirror, kept in sync by hand" treatment `GraphDocument`'s own doc comment already accepts — for an Immer-compatibility reason here rather than a module-boundary one. The `@forge/dialogue` dependency this ADR implied `project-export` would need was added, then removed once the independent declaration made it unnecessary.

**Migration:** a document persisted with the old `{speaker, text}` shape converts losslessly to a one-node tree with no `choices` (`migrateEntityDialogue`, wired into the existing `migrateEntityPlacement`) — `@forge/dialogue` already ends a dialogue after any node with no choices, the exact behavior a bare one-liner always had. An already-widened tree (real or fixture-authored, since M10 doesn't exist yet to author one through the UI) passes through untouched, not re-wrapped.

**`packages/player`'s `PlayerEntityPlacement.dialogue` narrowed to `unknown`** (from `{speaker, text}`) rather than widened to match: its own doc comment already stated only *presence* is ever read (`gameLogic.ts`'s `if (placement.dialogue) dialogueCapableNpcIds.add(...)` — confirmed by grep, nothing else touches the field), so widening its declared shape to track every future `EntityDialogue` change would be churn with no reader to serve. This is honestly a narrowing of a public-ish type, done because the real usage was already narrower than the old type claimed.

**Proof, not assertion:** `packages/project-export/test/documentTypes.test.ts` gained migration tests for the legacy-shape conversion, an already-widened tree passing through unchanged (including its `choices`), and an entity with no dialogue authored migrating with no `dialogue` key at all. `packages/project-export/test/toExportProjectInput.test.ts`'s existing dialogue fixtures were updated to the tree shape (regex-based error-message assertions needed no changes). `packages/editor/src/preview/protocol.ts`'s `isValidEntity` — a real *runtime* structural validator for the cross-origin preview bridge, not just a TS type — gained `isValidDialogueNode`/`isValidDialogueChoice`, with new tests in `protocol.test.ts` covering an empty-nodes rejection, a malformed-node-within-a-tree rejection, a valid multi-node branching tree acceptance, and a malformed-choice-within-a-node rejection. `EntityInspector.tsx`'s existing quick one-line dialogue form now edits `dialogue.nodes[0]`'s `speaker`/`text` only, explicitly leaving any further nodes and that node's own `choices`/`locale`/`autoAdvanceSec` untouched (a real test proves this — editing node 0 through a hand-authored branching fixture leaves `choices` and node 1 intact) — a deliberately narrower bridge than the eventual `DialogueTreeEditorDialog` (M10), not a replacement for it. The full editor suite (472 tests, four new) and the CLI's real `forge export` smoke tests (which already exercise an entity with dialogue authored, per the `starter-rpg` fixture) stayed green throughout — the live preview's own `rebuildDialogueRuntime` needed no changes at all, since it already delegated to `buildDialogueTreesFromEntities`, and a hand-authored multi-node tree already works correctly through it, unverified by a dedicated exit-criteria proof until M13.

## Addendum (M10): `DialogueTreeEditorDialog` — the real branching authoring surface

Per Decision 2's own framing ("deliberately NOT graph-authored... a conversation is a list with jump points, not a typed-socket wiring problem"): a full-screen `Dialog` (`packages/editor/src/dialogue/DialogueTreeEditorDialog.tsx`, matching `GraphEditorDialog`'s own shape) with a `Tree`-based "Dialogue Outline" (speaker/text preview per line, the same keyboard/screen-reader-parallel treatment `GraphEditorDialog`'s "Graph Outline" already gives the canvas), a per-line form (speaker/text/locale/auto-advance via the existing `JsonSchemaForm`), and a per-choice destination `<select>` over the tree's own node list — deliberately a plain native select, not `GraphEditorDialog`'s output/input two-step keyboard connect-picker, since a dialogue choice has exactly one destination.

**No new per-node/per-choice store commands** (unlike `GraphEditorDialog`'s `addGraphNode`/`moveGraphNode`/etc.): every edit computes a whole new `nodes` array via `dialogueTreeEditing.ts`'s pure helpers (`addDialogueNode`, `removeDialogueNode`, `moveDialogueNode`, `configureDialogueNode`, `addDialogueChoice`/`removeDialogueChoice`/`configureDialogueChoice`) and hands it to the dialog's `onChange`, which the container routes straight into the existing `configureEntityDialogue` action — already self-inverse and already JSON-diff no-op-suppressing, so this milestone needed zero new `ProjectCommand` variants. `openDialogueEntity: {sceneId, entityId} | undefined` (plus `openDialogueEditor`/`closeDialogueEditor`) is new, transient UI state mirroring `openGraphId`'s own treatment exactly — not persisted, not in the command log, cleared automatically if the entity being edited is removed (the same defensive clear `selection` already gets in `removeEntity`).

**A real correctness problem `dialogueTreeEditing.ts` had to solve, not sidestep:** `DialogueTreeChoice.next` is a plain array index into the tree's own `nodes`, so reordering or removing a node can silently point an existing choice at the wrong line — or at a line that no longer exists — unless every such edit remaps every choice's `next` in lockstep. `removeDialogueNode` redirects any choice that pointed at the removed node to `-1` (end dialogue), the same "target no longer exists" fallback `graph/remove-node`'s own edge cascade uses, and shifts every other `next` down to match; `moveDialogueNode` swaps two nodes and remaps every choice (including a self-referencing one) to keep pointing at the same *node*, not the same *position*. Both are proven with dedicated tests, not just exercised incidentally by UI interaction tests.

**Entry point:** `EntityInspector`'s existing quick one-line dialogue form gained an "Edit branching dialogue…" button (npc entities only), opening the dialog via the new `openDialogueEditor` action — the ADR's own Decision 2 framing that the quick form and the full editor coexist, not one replacing the other.

**Proof, not assertion:** `dialogueTreeEditing.test.ts` (17 tests) covers every pure helper in isolation, including the `next`-remapping correctness above. `DialogueTreeEditorDialog.test.tsx` (11 tests) covers all six required states' worth of interaction (empty/populated, add/remove/reorder a line, add/edit/remove a choice, boundary-disabled move buttons) against the presentational component directly. `DialogueTreeEditorDialog.stories.tsx` gives Empty/OneLine/Branching states a real Storybook story (verified via an actual `storybook build`). `DockviewPanels.test.tsx` gained a `DialogueTreeEditorDialogContainer` suite (4 tests) proving an edit lands in real, undoable `document` state — not local-only UI state — and that closing the dialog (a real `Escape` keydown through `Dialog`'s own handler) clears `openDialogueEntity`. `EntityInspector.test.tsx` gained coverage for the new button, including its absence on a player-start. The full editor suite (506 tests, 34 new) and the CLI's real `forge export` smoke tests stayed green throughout.

## Addendum (M11): data tables — module-api change, `ProjectDocument.dataTables`, `core:lookupRow`/`core:tableRowCount`, and full export/preview wiring

**The module-api change, additive, both halves.** `SetupContext.dataTables: Readonly<Record<string, readonly Readonly<Record<string, unknown>>[]>>` (table id → its rows, plain JSON — `packages/module-api/src/module.ts`) is delivered the identical "plain data in" way `config` already is: no new bridge mechanism, required (not optional) on the public interface since it's meant to be "always present" the same way `storage`/`log` already are — a data table is shared project data any module may read, not something a project opts a specific module into. A second, smaller addition this ADR's own text didn't originally enumerate turned out to be necessary while actually building the two new graph nodes below: `GraphNodeExecutionContext.dataTables` (`packages/module-api/src/graph.ts`), the identical value threaded straight through by `@forge/graph-runtime`'s interpreter from the owning module's own `ctx.dataTables` — a pure in-process pass-through, since `@forge/graph-runtime` is itself an ordinary module. Both were run through `api-extractor`'s `api-update` (`etc/module-api.api.md` regenerated twice, once per addition) per CLAUDE.md 3.1's own discipline.

**Required at the public boundary, optional-with-default one layer in.** `SetupContext.dataTables` is required — module authors get a real object, never `undefined`. `ModuleBridgeOptions.dataTables?` (`packages/runtime-host/src/module/moduleBridge.ts`), the internal runtime-host-facing plumbing layer, is optional, defaulting to `{}` inside `ModuleBridge.create()` (`options.dataTables ?? {}`) — deliberately, to keep the blast radius small on every pre-existing internal call site (test harnesses, `smokeRunner.ts`, `gameLogic.ts`) that has nothing to do with data tables yet, while still guaranteeing the guest-facing `ctx.dataTables` is always real. `createModuleRuntime` (`packages/editor/src/preview/directModuleHost.ts`, the editor's unsandboxed live-preview path) got the same optional-fourth-parameter treatment for the identical reason.

**`ProjectDocument.dataTables: Record<string, DataTableDefinition>`**, `DataTableDefinition = {id, name, columns: DataTableColumn[], rows: Record<string, unknown>[]}` (`packages/project-export/src/documentTypes.ts`) — deliberately loose rows (`Record<string, unknown>`, not one union-typed field per declared column type): a JSON-Schema-driven, per-column-typed row shape would need the same generic-cell-editor machinery a real spreadsheet component needs, and M12's own `DataTableEditorDialog` (TanStack Table) *is* that machinery — this type just carries what it produces. `columns`/`rows` are both mutable (not `readonly`) arrays, the identical Immer-`Draft<T>`-inside-a-discriminated-union constraint M9's own addendum already documented for `DialogueTreeNode.choices` — reapplied here proactively rather than rediscovered the hard way a second time. `migrateDocument` defaults a missing field to `{}` for any pre-M11 document, the same treatment `quests`/`graphs` already got at their own introduction.

**`core:lookupRow`/`core:tableRowCount`** (`packages/modules/graph-nodes-core/src/nodes/dataTables.ts`) — both pure (a table read has no side effect, the same reasoning `core:getComponent` already gives), reading `ctx.dataTables` directly rather than an event round-trip: unlike `core:questIsActive`'s `quest:query`/`quest:queried` pattern (a *live module's* mutable runtime state, reached only through its own event surface), a data table is read-only project data delivered straight into the execution context already — there is nothing to ask a module for. `table`/`keyColumn` are `config` values, the same authoring-time treatment `core:getComponent`'s `component` name already gets; a missing/unknown table degrades to an empty result (`null` row, `0` count) plus `ctx.warn`, never a throw, matching every other pure node here on a partially-authored graph. Editor palette metadata (`nodeRegistry.ts`, category "Data Tables") was added in the same commit as the node types themselves.

**A real, pre-existing bug found and fixed along the way, not merely worked around:** `NODE_REGISTRY`'s own construction (`packages/editor/src/graph/nodeRegistry.ts`) throws if any `@forge/graph-nodes-core` node type lacks registered editor metadata — and the four M7 quest node types (`core:questStart`/`core:questCompleteObjective`/`core:questIsActive`/`core:questIsObjectiveComplete`) had none. This went undetected through M7–M10 because `@forge/graph-nodes-core`'s `dist/` (gitignored, not rebuilt by a plain `pnpm run test`/`pnpm run typecheck` unless something upstream forces it) still predated the quest nodes' addition — the editor was silently testing and typechecking against a stale build the whole time. Rebuilding `@forge/graph-nodes-core` for M11's own new node types surfaced the crash immediately (`nodeRegistry.test.ts` failing with "no editor metadata registered for node type \"core:questStart\""). Fixed by adding the missing four entries (category "Quests") alongside the two new M11 entries, rather than leaving it for a future milestone to trip over. **Lesson for the rest of J1 and beyond: a workspace-wide `pnpm run build` (not just `test`/`typecheck`, which can silently run against stale `dist/` for any package whose build script wasn't independently re-run) is the only way to be sure a cross-package addition doesn't have this exact blind spot** — added to this session's own working discipline, not merely noted here.

**A related, separate, and still-open gap, deliberately not fixed in M11 (flagged for M13, not silently absorbed into this milestone's scope):** `@forge/quests` itself is not wired into the editor's live preview (`PreviewApp.tsx`) at all — that file hand-constructs a runtime per first-party module (dialogue, inventory, graph-runtime), and quests was never added to that list at M7 or M8. A quest graph (`core:questStart` etc.) authored and tested live in the preview today has no listener for `quest:start`/`quest:query` — the node emits into the void. This is exactly the kind of gap M13's own exit-criteria proof ("a real quest... verified live in the preview") exists to catch honestly rather than assume away; recorded here explicitly so M13 starts from a known, not rediscovered, gap.

**Export-pipeline and preview wiring, both real, both tested:** `toExportProjectInput.ts` builds `PlayerProjectData.dataTables` (`packages/player/src/playerProjectData.ts`, a new required field) by stripping each `DataTableDefinition` down to its `rows` only — `columns`/`name` are editor/CSV-import authoring metadata nothing at runtime ever reads. `packages/cli/src/commands/export.ts`'s hand-authored `--project` fixture path (`fixtures/projects/starter-rpg/project.json` and friends) treats `dataTables` as optional-with-default (`raw.dataTables ?? {}`), with real structural validation when present — the same "an existing fixture from before this field existed keeps exporting unchanged" treatment already established for `ModuleBridgeOptions.dataTables?`. `gameLogic.ts` (`packages/player`) threads `projectData.dataTables` into every installed module's `ModuleBridge.create()` call, identically, project-wide — not per-module. On the live-preview side, `PreviewSceneMessage.dataTables` (`packages/editor/src/preview/protocol.ts`, with a real runtime structural validator, `isValidDataTableRows`) carries the same rows-only shape from `PreviewPanel.tsx` (re-sent on every scene message, mirroring `graphs`) through to `PreviewApp.tsx`, which threads it into `@forge/graph-runtime`'s own `createModuleRuntime` call — the only first-party module in the live preview that actually consumes `dataTables` today, since (per the gap noted above) `@forge/quests` doesn't run there and dialogue/inventory have no use for table data.

**Proof, not assertion:** `packages/modules/graph-nodes-core/test/dataTables.test.ts` (5 tests) covers a successful lookup, a no-matching-row lookup (empty result, no warn — a normal "not found" isn't a graph author error), a missing-table lookup (empty result plus warn), and both row-count paths. `packages/modules/graph-nodes-core/test/index.test.ts` and `packages/editor/src/graph/nodeRegistry.test.ts` were updated for the two new node types and (having surfaced the pre-existing bug above) the four quest node types' new editor metadata. `packages/project-export/test/toExportProjectInput.test.ts` and `packages/editor/src/store/projectStore.test.ts`/`shell/PreviewPanel.test.tsx`/`preview/protocol.test.ts` all exercise the widened document/message shapes, including a real non-empty data table passed end to end through `migratePersistedProjectState`'s "current-shape document, unchanged" test. A full workspace `pnpm run build` (every package, not just the ones touched directly) and the full `pnpm run test`/`pnpm run typecheck` (all 506 editor tests, all `@forge/graph-nodes-core`/`@forge/graph-runtime`/`@forge/quests`/`@forge/dialogue`/`@forge/inventory`/`@forge/turn-battle` suites, and the CLI's real `forge export` smoke tests including the `starter-rpg` and marketplace-guest-bundle fixtures) stayed green throughout — the build discipline this milestone's own "Lesson" paragraph above now requires explicitly, not merely hoped for.
